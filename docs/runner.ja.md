# 評価ケースの実行

[English](runner.md) | **日本語**

このページでは，提出物を評価ケースで実行する方法（`spacecraft_ops_challenge.judge.runner`）について説明します。
各評価ケースは，それぞれ新しい2つのプロセスで実行され，評価ケースを参加者のコードから切り離します。
評価ケースの実行には Linux または macOS が必要で，それ以外では `run_case` が `RuntimeError` を送出します。

```python
from pathlib import Path

from spacecraft_ops_challenge.judge.public_scenarios import PROVIDER, public_suite
from spacecraft_ops_challenge.judge.runner import run_suite
from spacecraft_ops_challenge.judge.submission import extract_submission

submission = extract_submission("submission.zip", Path("work/extracted"))
for outcome in run_suite(submission.root, public_suite().cases, PROVIDER):
    print(outcome.case_id, outcome.status, outcome.metrics, outcome.participant_cpu_s)
```

`run_case(submission_root, case, provider)` は1つの評価ケースを実行し，その `CaseOutcome` を返します。
`run_suite(submission_root, cases, provider)` はすべての評価ケースを順に実行し，その結果を返します。
失敗した評価ケースがあっても `run_suite` は止まらず，`on_case_done` が各結果とともに，結果が得られるたびに呼び出されます。
どちらも次のキーワード引数を受け取ります。

| 引数 | 意味 |
|---|---|
| `timeout_s` | 1つの評価ケースの実時間の上限（デフォルトは `DEFAULT_CASE_TIMEOUT_S`，300 秒） |
| `env` | 評価ケースのプロセスの環境変数（デフォルトは現在のプロセスの環境変数） |
| `overlay` | 参加者のパッケージの `Overlay`（[参加者のパッケージ](dependencies.ja.md)を参照），または `None` |

評価ケースと `ScenarioProvider` については，[評価ケース](judge.ja.md)を参照してください。

## 評価ケースごとの2つのプロセス

各評価ケースは，現在のインタプリタから新しい Python プロセスを2つ起動します。

```text
呼び出し側
└── 信頼された実行プロセス：評価ケース，そのシナリオ，シミュレータ
    └── 参加者のプロセス：submission/strategy.py:MyStrategy とそのパッケージ
```

信頼された実行プロセスは，評価ケースと `ScenarioProvider` を標準入力から受け取ります。
`ScenarioProvider` でシナリオを作成し，`run()` と `evaluate()` で実行します（[シミュレーション](simulation.ja.md)を参照）。
その戦略は，すべてのコールバックを参加者のプロセスに転送します。
参加者のプロセスには，`ScenarioProvider` が実行される前の環境変数を渡すため，
`ScenarioProvider` が設定した環境変数は参加者のプロセスに届きません。
結果は，参加者のファイルとは別の一時ディレクトリにあるファイルに書き込みます。

参加者のプロセスは，`spacecraft-ops-challenge run` と同じように，
`submission/` をインポートパスの先頭に置いて `submission/strategy.py:MyStrategy` を読み込み，
評価ケースのためにインスタンスを1つ作成します。
このプロセスが受け取るのは，戦略が見てよいもの，つまり `MissionBrief`，テレメトリ，`Commander` への要求の結果だけです。
評価ケースの ID，`payload`，`ScenarioProvider`，シナリオ，そのシードや `Modifier`，真の状態は決して受け取らず，
評価ケースを定義するモジュールも `ScenarioProvider` もインポートしません。
コマンドライン引数は，ソケットのファイル記述子，提出物のコピーのディレクトリ，`Overlay` がある場合はそのディレクトリです。
標準入力は空です。

## メッセージ

2つのプロセスは，標準出力や標準エラー出力とは別の，専用のソケットの組で通信します。
各メッセージは JSON オブジェクトで，その前に長さを4バイトのビッグエンディアン整数で置きます。
1つのメッセージは最大 `MAX_MESSAGE_BYTES`（16 MiB）です。

- 参加者のプロセスは，戦略を読み込んだ後，準備ができたこと，または読み込みエラーのトレースバックを報告します。
- `initialize` は `MissionBrief` と初期テレメトリを，`update` は最新のテレメトリを運びます。
- コールバックの間，参加者の `Commander` はすべての要求を信頼された実行プロセスに送ります。
  信頼された実行プロセスはそれを自身の `Commander` で実行し，結果を返すか，参加者の側で送出される `CommandError` のメッセージを返します。
  そのため，タイムラインの意味は[コマンドとタイムライン](timeline.ja.md)のとおりです。
- コールバックの終わりに，参加者のプロセスは，コールバックが戻ったこと，または送出された例外を報告します。

戦略の例外や捕捉されなかった `CommandError` は，ローカルでの実行と同じく，
実行を `STRATEGY_ERROR` または `INVALID_COMMAND` で終了させ，終了の詳細には参加者のトレースバックが含まれます。
100 000 文字を超えるトレースバックは，先頭と末尾の 50 000 文字ずつを残します。
プロトコルに従わないメッセージは，評価ケースを `CRASHED` で終了させます。

## 評価ケースごとの新しい状態

評価ケースごとに参加者のプロセスが新しくなるため，参加者のコードのモジュールのグローバル変数，キャッシュ，クラスの状態が評価ケースの間で引き継がれることはありません。
各評価ケースは展開したファイルの新しいコピーで実行されるため，戦略が書き込んだり変更したりしたファイルが，後の評価ケースや元のファイルに影響することもありません。
参加者のプロセスの作業ディレクトリは，`submission/` を含む，そのコピーのディレクトリです。

## 出力の取得

評価ケースのプロセスは `PYTHONUNBUFFERED=1` で実行されるため，クラッシュや時間切れの場合でも出力は失われません。
標準出力と標準エラー出力は，結果の `stdout` と `stderr` として別々に取得されます。
信頼された実行プロセス自身が Python の `sys.stdout` と `sys.stderr` に書いた出力は，
`ScenarioProvider` の出力や警告も含めて破棄されるため，取得される出力は参加者のものです。
それぞれ最大 `MAX_OUTPUT_BYTES`（100 000 バイト）で，先頭と末尾の 50 000 バイトずつを保持し，
その間に `... [N bytes omitted] ...` という行を挟みます。
出力は評価ケースの実行中に読み取られるため，終わらない出力が評価ケースを止めることはありません。

## 結果

`CaseOutcome` は次のフィールドを持ちます。

| フィールド | 意味 |
|---|---|
| `case_id` | 評価ケースの ID |
| `status` | `CaseStatus`（下記を参照） |
| `metrics` | 完了した評価ケースでは実行の `RunMetrics.to_dict()`（[評価](evaluation.ja.md)を参照），それ以外では `None` |
| `detail` | 戦略のトレースバックなどの実行の終了の詳細，または評価ケースが完了しなかった理由 |
| `missing_module` | `detail` 中の `ModuleNotFoundError` が示すモジュール（あれば） |
| `stdout`，`stderr` | 取得した出力 |
| `duration_s` | 評価ケースの実時間（秒） |
| `participant_cpu_s` | 参加者のプロセスの CPU 時間（秒，下記を参照），または `None` |
| `worker_error` | 信頼された実行プロセス自体の失敗のトレースバック，または `None` |

| `CaseStatus` | 意味 |
|---|---|
| `COMPLETED` | 実行が，正常にまたは戦略のエラーによって終了し，`metrics` がある |
| `LOAD_ERROR` | `submission/strategy.py:MyStrategy` をインポートまたはインスタンス化できなかった |
| `CRASHED` | 実行が評価指標を生成しなかった。戦略が `SystemExit` や `KeyboardInterrupt` を送出した，そのプロセスが終了した，プロトコルに違反した，または信頼された実行プロセスが評価ケースの評価に失敗した |
| `TIMEOUT` | 評価ケースが `timeout_s` を超えた |

`ScenarioProvider` が例外を送出した場合など，信頼された実行プロセス自体が失敗した場合は，
そのトレースバックに `ScenarioProvider` や評価ケースのデータが現れうるため，`detail` には例外の型だけを示します。
トレースバックは，評価を実行する側のために `worker_error` に記録されます。

`to_dict()` は JSON に変換できるデータを返し，`CaseOutcome.from_dict` はその逆変換です。
`from_dict` は，結果を表さないデータに対して `ValueError` を送出します。

## 参加者のプロセスの CPU 時間

`participant_cpu_s` は，参加者のプロセスのユーザー CPU 時間とシステム CPU 時間の合計です。
完了した実行の後，信頼された実行プロセスは接続を閉じ，参加者のプロセスは終了します。
信頼された実行プロセスは，そのプロセスを `os.wait4` で回収し，`os.wait4` が報告する時間を記録します。

- 参加者のプロセスのすべてのスレッドと，そのプロセスが行ったすべての処理を含みます。
  インタプリタの起動と戦略の読み込みから最後のコールバックまでで，メッセージの変換のうち参加者の側の処理も含みます。
- 信頼された実行プロセスとシミュレータは含みません。
  参加者のプロセスがそれらを待っている間は，CPU 時間を使いません。
- Linux では，参加者のプロセスが起動したプロセスは，参加者のプロセスが終了する前に終了し，参加者のプロセス自身または含まれる別のプロセスによって待たれた場合にだけ含まれます。
  参加者のプロセスが終了したときにまだ実行中のプロセスは含まれません。

`LOAD_ERROR`，`CRASHED`，`TIMEOUT` の評価ケースでは `None` です。
実行の後 5 秒以内に参加者のプロセスが終了しない場合と，`os.wait4` がないプラットフォームでも `None` です。

## 時間の上限と後始末

`timeout_s` は，インタプリタの起動と戦略の読み込みを含む，評価ケース全体の実時間を制限します。
これを超えた評価ケースは，停止される間に信頼された実行プロセスが結果を書き込んだとしても `TIMEOUT` です。

どちらのプロセスも処理の直後に終了するため，残されたスレッドや終了時の処理が評価ケースを遅らせることはありません。
信頼された実行プロセスは新しいセッションで起動し，参加者のプロセスはそのプロセスグループに属します。
信頼された実行プロセスが終了したとき，または時間の上限に達したとき，そのプロセスグループに残っているすべてのプロセスを停止します。
これには，参加者のプロセスと，そのプロセスが起動したプロセスが含まれます。
戦略が新しいセッションやプロセスグループに移したプロセスは，そのグループの外にあり，評価ケースの後も残ることがあります。
参加者のプロセスなど，停止した信頼された実行プロセス以外のプロセスは，init プロセスが回収します。
コンテナでは，`docker run --init` などで，親を失ったプロセスを回収する init プロセスを実行し，ゾンビプロセスが残らないようにしてください。

## 参加者のパッケージ

`Overlay` は参加者のプロセスだけが，`PYTHONPATH` の先頭に受け取ります。
参加者のプロセスは `Overlay` のディレクトリにある `.pth` ファイルも処理し，戦略が起動したプロセスは `PYTHONPATH` を引き継ぎます。
信頼された実行プロセスは現在の環境のパッケージだけで実行されるため，コアパッケージのモジュールを含む `Overlay` であっても，信頼された側を置き換えることはできません。

## この境界の意味

プロセスを分けることで，評価ケースとシミュレータは，参加者のコードによる通常の内部調査から切り離されます。
これは設計上の境界であり，悪意のあるコードに対する隔離環境ではありません。
参加者のプロセスは，評価ケースを実行するコードと同じユーザーとして，同じファイルシステムへのアクセス権で実行されます。
